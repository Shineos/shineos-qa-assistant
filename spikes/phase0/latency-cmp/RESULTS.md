# モデル別レイテンシ比較実測（2026-09-14）

同一4質問×3モデル、UIと同一の `/api/chat` SSE 経由（サーバ側ストップウォッチ）。
マシン: Ryzen 7 5700U (8C/16T) / RAM 15GB / CPU-only / ctx 2048 / スレッド8。
質問: q1=国内出張の日当 / q2=交通費の精算方法 / q3=慶弔休暇の日数 / q4=天気(ガード)。

| 計測 | 1.7B (quick) | 4B-2507 (standard) | 30B-A3B MoE (UD-Q3_K_XL) |
|---|---|---|---|
| q1 コールド初回 TTFB / 合計 | 10.3s / 11.2s | 17.6s / 19.4s | 33.2s / 36.9s |
| q1 ウォーム再質問 TTFB / 合計 | 4.0s / 4.9s | 3.8s / 5.7s | 3.8s / 5.4s |
| q2 新規質問 TTFB / 合計 | 6.0s / 8.4s | 8.2s / 13.3s | 13.6s / 17.9s |
| q3 新規質問 TTFB / 合計 | 6.7s / 12.6s | 8.4s / 18.7s | 10.7s / 22.4s |
| q4 ガード拒否 | 3.1s | 2.9s | 3.1s |
| LLMエンジンRAM (WS) | 2.0GB | 4.5GB | 9.5GB (mmap, ファイルバック除く) |
| 生成速度 (観測) | ~20 t/s | ~10 t/s | ~12-15 t/s |

## 結論
1. **新規質問のレイテンシは 1.7B < 4B < 30B**。30B は生成(tg)は高速でも
   MoE のプロンプト処理(pp)が遅く、新規質問のTTFB・合計とも最も遅い。
   先行の「tg 14.1 t/s で4Bより40%高速」は生成フェーズのみの話で、
   RAGフロー全体では逆転する。
2. **ウォーム（同一質問・プレフィックスキャッシュhit）は3モデル同水準（~5s）**。
   ここは埋め込み+リランクのパイプライン固定費（~4s）が支配。
3. **1.7B は思考モード無効化（enable_thinking=false）で大幅改善**:
   修正前は隠れ<think>推論に300トークン予算を全消費して空回答になることが
   あり（q3で0文字）、TTFBも+8s。修正後は最速・正答。
4. **30B は16GB機なら動作可能**（--no-repack + mmap、WS 9.5GB）だが、
   初回回答まで33s、新規質問TTFB 11-14s。「品質優先モード」として
   カタログ提供する価値はあるが、既定には不向き。8GB機は不可。
5. コールドスタート（初回質問の体感）: 1.7B 10s / 4B 18s / 30B 33s。

## 実施中に発見・修正した不具合（本実測の副産物）
- **Job Object が一度も機能していなかった**: JOBOBJECT_BASIC_LIMIT_INFORMATION
  の Affinity を uint(4B) で宣言し構造体サイズが不正 → SetInformationJobObject
  が常に失敗（旧コードは黙殺）→ エンジン孤児化の真因。ULONG_PTR 化で修正、
  バックエンド強制終了時に子3プロセス全滅を確認。
- **tier変更で embed/rank が永久停止**: POST /api/settings の StopAll 後に
  再起動する者がいない → 以後の全チャットが接続拒否。StartEmbedAndRank を
  自己修復化し ChatFlow/Ingest から呼ぶよう修正。
- **エンジンログFileStreamリーク**: Start 途中の例外でハンドルが残り再起動が
  永久失敗。FileShare.ReadWrite でロック不耐化。
- **Qwen3-1.7B の隠れ思考**: chat_template_kwargs enable_thinking=false 追加。
- 開発機に ASP.NET 共通ランタイムが無く exe 直起動不可。tools/dotnet-sdk の
  DOTNET_ROOT 指定か、製品では自己完結publishが必須。

測定スクリプト: measure.ps1 / questions.json（同ディレクトリ）、
生回答: answers/*.txt、生ログ: output/backend-dev-data/logs/。

# 高速化改修の効果（2026-09-14 第2ラウンド）

## 実装した改修
1. **高信頼リランク省略**: ハイブリッドtop1の生cos≥0.70 かつ kw≥0.15 なら
   リランク（実測~2.2s）をスキップして上位2件を採用。さらに cos≥0.72・kw≥0.35
   の超高信頼は文書1件のみ注入。実測分離: hit質問 cos=0.70-0.75 / nohit(天気) cos=0.46。
2. **プロンプト再構成**: RAG文脈をsystem内から最終userメッセージへ移動。
   system(静的)+履歴 がプレフィックスキャッシュで丸ごとヒットし、
   2往復目以降は履歴分（~500トークン）のppを削減。
3. **SystemPromptスリム化**: ~25%短縮（455→336-368トークン/リクエスト）。
4. **LLM起動時事前ロード**: 初回質問がモデル読込を待たない。
5. **LLM優先度 Normal + -ub 2048**: BelowNormalはpp-24%だったため。
6. **プロンプト版数管理**: prompt_version設定で回答キャッシュ自動無効化。

## 効果（同一質問・同一マシン、機械負荷ゆらぎ±15%あり）

| シナリオ | 改修前 | 改修後 |
|---|---|---|
| 1.7B ウォーム再質問 TTFB/合計 | 4.0s / 4.9s | **0.15s / 1.1s** |
| 1.7B 新規質問 TTFB（q2/q3） | 6.0-6.7s | **3.5-4.6s** |
| 1.7B 初回質問（起動直後） | 11.2s | **7.2s** |
| 4B ウォーム再質問 TTFB | 3.8s | **0.2s** |
| 4B 新規質問 TTFB（q2/q3） | 8.2-8.4s | 8.5-11s（ゆらぎ内・トークン-25%） |
| 4B follow-up質問（履歴あり）TTFB | （推定~20s相当） | 11.7s |
| 30B ウォーム再質問合計 | 5.4s | **2.0s** |
| ガード拒否（全モデル） | ~3s | ~3.5s（不変・正常動作） |

## 判明した上限要因
- **4Bのppは実運用時~44 t/s**（エンジン常駐下）。単体ベンチ56 t/sとの差は
  システム負荷（常駐embed/rank・OS）。プロンプトトークン数が唯一の実効レバー。
- **回答が長文化**: 新プロンプト（文脈をuserに統合）で4Bは詳細な箇条書きを
  返すようになった（q2: 69→182字）。TTFBは改善しても合計時間は生成長依存。
- スレッド: t8が最適（t16はpp+11%だがtg-19%）。fa=on優位（pp 43.1 vs 40.8）。

# 初回回答の高速化（2026-09-14 第3ラウンド）

## 実装
1. **起動時ウォームアップ**: LLMモデル読込後にダミー1トークン生成で計算グラフ
   構築とシステムプロンプトのスロット接頭キャッシュを先行作成（Supervisor内。
   起動・idle復帰・モデル切替の全経路で発火）。embed/rankもダミー呼出で暖気。
2. **モデル選択時に即ロード**: 送信フォーム/設定でモデル選択した瞬間に
   バックグラウンドでエンジン読込開始（質問入力中にロードが進む）。
3. **キャッシュヒットはLLMを待たない**: 回答キャッシュ判定をEnsureLlmより前に移動。
   エンジン未ロードでも同一質問に即答（実測153ms）。
4. **リランク省略閾値緩和**: cos≥0.70→0.62・kw≥0.15→0.10。
   実測分離（hit 0.68-0.75 / nohit 0.46）に対し余裕を持たせ、境界のhit質問も省略。

## 1.7Bの「最初の一文字まで」実測
| シナリオ | TTFB |
|---|---|
| 起動直後に即質問（ロードと競合する最悪ケース） | 5.2s（改修前6.2s） |
| ウォームアップ完了後・明確なhit質問（skip) | 3.5〜4.6s |
| 境界質問（リランク経由） | 6〜7s |
| 同一質問（回答キャッシュ・エンジン不要） | **0.15s** |
| nohit質問（ガード拒否） | ~3.5s |

## 残る理論下限（skip時）
TTFB ≈ 埋め込み0.3s + pp(文脈+質問 ~370tok ÷ 120t/s ≈ 3.1s) ≈ **3.4s**。
これを切るにはスニペット短縮・軽量子化・小型モデルのいずれかで品質トレードオフ。
リランク経由（境界・nohit）は~2.5s追加されるが、これは誤回答防止のガード精度に必要。

# 失敗2ケースの根本原因と解決（2026-09-14 第6ラウンド）

## s04 経費精算手順 — RAGチャンキング境界問題 → **解決済み**
- 原因: 350字チャンク境界が手順5ステップの途中（step3直後）で分断。
  検索には「経費精算の手順」見出しを持つ前半チャンク（step1-3）のみ流入し、
  step4領収書添付・step5承認申請はモデルが一度も参照できなかった。
  モデルは見えた範囲を正確にならべ、閉じとして「完了ボタン」を補完（幻覚）。
  **全構成で同一失敗=モデル・量子化ではなく注入文脈の欠落が原因。**
- 解決: **隣接チャンク連結** — 採用チャンク(seq)の本文に次チャンク(seq+1)を連結して
  からスニペット抽出窓（240字）を適用。窓が境界をまたいでstep4-5まで到達。
  連結済みの続きチャンクがtop2に入った場合は二重注入をスキップ。
  実装: chunks.seqをインデックスに保持（Db.ChunkRow/ChunkIndex.Rec/NEXT取得）、
  ChatFlowの文脈構築と出典プレビューの両方で連結テキストを使用。
- 検証: s04全ステップ（領収書添付・上司の承認申請含む）を正答。**4B-IQ4_XSは18/18満点**。

## s07 長期出張の承認者 — 1.7Bの能力上限 → **階級設計で対応（既定方針どおり）**
- 原因: 規程文「承認は所属長。1週間を超える出張は部長の承認が必要」は
  同一チャンク内にあり検索は成功。だが1.7Bは「1週間超→部長」の条件束ねが
  できず、より顕在な「所属長」に引きずられる。両量子化で同一誤答。
- 実施した緩和策（効果なし）: SystemPromptに「条件と対象の対応を混同しない」指示を追記。
  → 1.7Bは改善せず。プロンプトでは解決不能な推論限界。
- 結論: **精度重視の質問は標準（4B）階級で使う**という階級設計の役割分担どおり。
  4B/IQ4_XSは正答（s07 PASS）。
- 追加観察: 1.7Bは慶弔一覧（s03）も実行ごとに列挙⇔圧縮要約が揺らぐ
  （スロットキャッシュ状態によるgreedyパスの分岐）。逐次性が必要な運用では4B推奨。

## 対策後の最終スコア
| 構成 | スコア |
|---|---|
| 1.7B IQ4_XS + 対策 | 16〜17/18（s07は能力上限、s03は揺らぎ） |
| **4B IQ4_XS + 対策** | **18/18** |

なお、s05（タクシー条件）は初回の期待キーワード設定が過剰（「禁止」の文字列も必須）
だったため緩和。回答自体「22時以降に帰宅する場合」で正答だった。

## 第10ラウンド: モデル破損時の無応答の本質対応（2026-09-14）

d2テストで発見した「破損GGUFでチャットが240秒無応答」について、テスト基準の緩和ではなく
コード上の根本原因を特定・修正した。

### 根本原因（4層の重畳）

1. **`WaitHealthy(port, 120)` がプロセス死亡を無視**: 破損モデルでllama-serverは0.07秒で異常終了するのに、
   ヘルス待ちは120秒満値まで待つ（死体を2分看取る）
2. **OOM誤診フォールバック**: `EnsureLlm`のcatchが失敗原因を問わずOOM扱いし、quick階級（最小）でも
   「quick→quick」の同一破損ファイル再試行を行い、待ち時間が2倍（計240秒）になる
3. **起動前整合性検証の未実装**: カタログ（Models.cs）に全モデルのSHA256があるのに検証せず、
   決定的失敗を「起動→瞬死→待ち」で発見していた（設計書のSHINE_E_MODEL_HASHが未実装だった）
4. **サーキットブレーカーなし**: 連続失敗後もチャットのたびに上記240秒を最初から繰り返す

### 対策と実測

| 対策 | 実装 |
|---|---|
| 起動前SHA256検証（永続キャッシュ `{data}/model-verify.txt`、len+mtimeキーで再ハッシュ回避） | `ModelIntegrity.Verify` を全エンジン起動時に適用 |
| ヘルス待ちの瞬死検知 | `WaitHealthy(port, sec, proc)` — プロセス退出で即false |
| OOM誤診の阻止 | SHINE_E_MODEL_HASH（InvalidDataException）はフォールバックせず即throw。フォールバック先が同一ファイルなら再試行しない |
| サーキットブレーカー | 連続3回失敗で即時エラー（モデル再DL完了・階級切替でリセット） |
| 利用者への伝達 | SSE `error` イベント `SHINE_E_MODEL_HASH`「モデルが破損しています。設定画面から再ダウンロードしてください」 |

**実測: 破損モデルでのチャット応答 240秒無応答 → 2,543ms でSHINE_E_MODEL_HASHエラー（約100倍）**。
起動時の整合性検証は embed 605MB+rank 606MB+1.7B 1.0GB で計約4秒（1回のみ、以後キャッシュ命中で0コスト）。
破損検出は `model integrity check FAILED: ... expected a02e41d3208e… got 63497BF7…` としてログに記録される。

## 第11ラウンド: 「再ダウンロード」導線の完了と追加発見（2026-09-15）

第10ラウンドの残課題を検証した結果、**案内だけあって実際には修復できない導線だった**ため完了させた。

### 発見1: 再ダウンロードが破損ファイルで無音のno-op

`InstallAsync` が `if (File.Exists(dest)) return;` で既存ファイルをスキップするため、
破損ファイルが存在する限り「再ダウンロードしてください」の案内に従っても何も起きなかった。

**対応**: ①既存ファイルのSHAを照合し、不一致なら削除して再DL（強制修復）。
②`/api/models` に `corrupted` フラグ追加（検証キャッシュ参照・ハッシュ計算なし）。
③モデルメニュー・設定画面に「破損」バッジ＋「再ダウンロード」ボタンを表示。

### 発見2: 回答キャッシュが破損検証テストを非決定型にする

修復後に同一質問をすると回答キャッシュ（LLM起動より前に評価）がヒットし、モデル破損中でも
正常回答が返る。**仕様として正しい**（過去の正答は有効）が、破損テストは `/api/cache-clear` から
始めるべき（d2スクリプトに追加）。

### 発見3: /api/models/progress が常に `{}`

`DownloadProgress` のメンバーがフィールド宣言で、System.Text.Jsonはフィールドをシリアライズ
しないため進捗APIが空オブジェクトを返していた（プロパティ化で修正、回帰テスト追加）。

### 検証済みの完全なユーザー旅程（実機）

1. GGUF破損 → チャット1回目 2.6秒で SHINE_E_MODEL_HASH エラー（cache-clear後）
2. 2回目 1.4秒でエラー → **3回目・4回目は67〜72msでサーキットブレーカー即時エラー**（起動時プリロード失敗込みで3連続到達）
3. モデルメニューに「破損」バッジ＋「再ダウンロード」ボタン表示（UIA/キャプチャで確認）
4. ボタンクリック → バックエンドが破損を検知し既存ファイル削除 → 1GBをHuggingFaceから再DL（167秒）→ SHA検証 → 完了
5. `corrupted` フラグ解除、チャットが正常回答に復旧

## 第12ラウンド: レイテンシ改善余地の定量的検証（2026-09-15）

「レイテンシに改善余地があるか」に対して、8問×2周プローブ（`lat-probe.ps1` 方式・毎回キャッシュクリア・
ユニーク接尾辞でキャッシュヒット排除）で実験した。

### TTFBの現状と支配要因

- 中央値 約4.0秒（quick 1.7B・ウォーム）。速い質問1.3〜2.5秒、遅い質問7〜10秒
- **リランクは16問中13問で既にスキップ済み**（rerank-skip gates実測ログ）→ 遅い質問のボトルネックは
  リランクではなく**プロンプトprefillのトークン数**（docs=2×240字スニペット＋質問＋履歴）

### 実験1: `--cache-reuse 128` ＋ KV量子化(`-ctk/-ctv q8_0`) → **却下**

8問すべてで悪化（+0.04〜+2.8秒）。CPUではKVのデクアント負担が帯域削減効果を上回る
（ctx 2048と小さいためKV帯域が元々小さい）。**実装から除外**。

### 実験2: スニペット圧縮（リランク入力240→160字・コンテキスト240→180字）→ **品質低下で却下**

- レイテンシ: 中央値 約4.0秒→約3.7秒（-8%。駐車場-20%）
- 品質: **Golden QA 118問が108→101に低下**（タクシー22時・会議室30日前・窓口内線等の事実が窓外に切断）
- **240字は実測上の最適点**（高速化と品質の両立点）。s04の教訓（切り詰めは事実を壊す）の再確認

### 結論: 現状がquick 1.7B・CPU構成の実用的な最適点

残る改善余地と評価:

| 施策 | 見込み | 評価 |
|---|---|---|
| モデル差し替え（より軽い0.6B等） | TTFB大幅減 | 品質低下が致命的（s07で1.7B既に能力上限近い）→ 非現実的 |
| より小さい埋め込みモデル（クエリ側のみ） | -0.1〜0.2秒 | 品質リスク大・効果小 → 優先度低 |
| リランク閾値緩和（さらにスキップ拡大） | -2秒（残り13%の質問のみ） | 誤ガードリスク → golden gate必須で要個別検証 |
| GPU端末（Vulkan） | TTFB大幅減 | 対象外（GPUなし前提の製品） |
| **モデル事前ロード維持（現状実装済み）** | — | 起動2秒・ウォーム済みで応答。既に最適化済み |

体感面は「同一質問0.2秒未満（回答キャッシュ）」「ウォーム新規質問中央値4秒」が現行の実力値。
重要問の速度を上げたい場合はstandard(4B)ではなくquick運用＋キャッシュで十分実用的。

## 第13ラウンド: 単一exe化（2GiB制限対応）のためのリランカ軽量化 → 却下（2026-09-15）

**目的**: GitHub Releasesの1アセット上限2GiBを超えるインストーラ（2.08GiB）を単一exe化するため、
リランカをQ8_0（606MB）→Q3_K_M（403MB）に置換（リランカは無状態のため埋め込みのような再ベクトル化移行が不要）。

**結果**:
- サイズ: インストーラ **2.08GiB→1.875GiB** で単一exe配布は達成可能
- 品質: **Golden QA 118問 = 103/118**（ベースライン帯105〜108を下回り、s14/t80の**拒否質問がガードをすり抜けて回答**）
- 原因: Q3_K_Mのリランクスコア分布がQ8と縮小 — 実測で**ヒット -0.1〜+1.3 / 非ヒット -2.2〜-6.0**（分離約2.1）に対し、
  Q8では非ヒット≤-7.8と分離5.8以上。ガード閾値-5.0はQ8の分布に対して設計されたもので、
  Q3_K_Mでは非ヒットの-2〜-5帯がすり抜ける。閾値を-2に詰める案もあるが、口語系の弱いヒット（-2前後）と
  重なるため誤拒否リスクが増え、分離マージンが恒常的に薄くなる

**決定: Q8_0に戻す**。「根拠のない回答をしない」ことが製品の核心であり、配布の利便性のために
ガード分離を狭めるトレードは不採用。単一exe配布はStore申請のパッケージURL（外部ホスティング）で解決する。
