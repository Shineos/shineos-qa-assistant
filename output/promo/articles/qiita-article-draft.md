## この記事で書くこと

- クラウドRAG(SaaS/Azure OpenAI等)ではなく「完全オフライン」を選んだ理由と、それが成立する条件
- Ollama等の中间層を使わず llama-server を直接起動する自作C#バックエンドの構成
- 「出典の偽装」を防ぐための検索ガード群の設計（今回の本題）
- 製造図面（表題欄・図番・スキャン）への対応

## 1. なぜオフラインか（99字に圧縮した動機）

製造業の現場文書（図面・仕様書・品質記録・顧客仕様）は「クラウドに置くこと自体が許されない」ことが多い。
SaaSのRAGは便利だが、社外秘をアップロードする時点で審査・稟議が落ちる。
→ 「文書も質問も回答も、そのPCから出ない」RAGなら、情報システム部門の審査を通る。

## 2. アーキテクチャ（中间層なし）

```
[WebView2 UI (TypeScript)]
   │  localhost:8300 (REST/SSE)
[自作C#バックエンド (SQLite, 検索, ガード)]
   │  127.0.0.1: 8301(llm) / 8302(embed) / 8303(rerank) / 8304(vision)
[llama-server x3-4 (llama.cpp公式プリビルド)]
```

- Ollamaを使わない理由: モデル配布・更新の制御を自前で持ちたい（SHA256検証付きDL、
  オフライン取り込み）、プロセスを閉じたら完全停止させたい（常駐しないことを審査で主張できる）
- 埋め込み: bge-m3 / リランク: bge-reranker-v2-m3 / チャット: Qwen3系のGGUF(IQ4_XS)

## 3. 検索と「出典の偽装」対策（本題）

ハイブリッド検索（BM25+ベクトル min-max合成）→ リランク → ガード、という一般的な構成に
見えるが、実運用で効いたのは「検索を通さない」ガードの方だった:

1. **リランク省略の罠**: 高速化のため「cos≥0.62 かつ kw≥0.10 ならリランクを省略」としていたが、
   KB外の質問が弱いキーワード一致（例: 「富士山の高さは？」が会議室文書に kw=0.37 で一致）で
   この短絡に入り、モデルが一般知識で回答、出典行の正規化によって**偽の出典が付いていた**。
   → 省略条件を kw≥0.50 に引き上げ、弱一致は必ずリランカー（クロスエンコーダ）で識別。
   学び: **kwスコアは正解質問(0.39-0.48)とKB外(0.37)を分離できない。分離器はリランカー**
2. **数値の捏造検知**: 回答中の2桁以上の数値が出典・質問のどちらにも無ければ、修正指示付きで
   1回だけ再生成（失敗したら元回答のまま。過剰に拒否しない）
3. **同一図番の混在**: 「ST-1042Aの材質は？」で改訂違いの2ファイルがヒットしたら、回答前に
   図面選択UIへ（正規形照合でハイフン/大小/全角の表記ゆれを吸収）
4. **対象語リルート**: リランカが意味的に近いけど対象語を含まないチャンクを採択した場合、
   拒否ではなく対象語を含むプール内チャンクへ差し替え

## 4. 製造図面への対応

- 表題欄の座標付き抽出（PdfPig）→ 図番・品名・材質・改訂をメタデータ化（正規化: "ST-1042A"≡"st1042a"）
- キャプチャ→WinRT OCR（4方向回転判定）→ 任意でQwen3-VLが表題欄を直接読取
- スキャンPDFは描画→OCR、さらにVLで全文書き起こしを索引に追加
- DXF（CAD図面）はTEXT/MTEXTエンティティを直接パース

## 5. 運用まわりの細かい話（記事の味付け）

- 配布: Inno Setupで47MBのliteインストーラ（モデル非同梱）→ 初回起動ウィザードでGGUFを
  SHA256検証付きDL。閉域PC向けにローカルGGUFの取り込み口も用意
- DLのスターループ: huggingfaceへの接続がバイト進展だけ停止することがあり、60秒の
  ストール監視→ミラーフォールバックを実装（実測で54MB停止を経験）
- 画像PDFから抽出器がICC辞書断片（「gTRC…(cprt」等）を疑似テキストとして返す問題 →
  印字不可能文字比率でジャンク判定してOCR/VL救済へ

## 6. 最後に（ソフト販売ではなく導入支援）

アプリ自体は無料。ストア審査（11条系ポリシー、署名、CRT同梱）を通した話や、
製造業の情報システム部門との接し方（30分オンラインデモ等）は別記事で。
