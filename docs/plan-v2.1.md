## 1. レイテンシの本質改善: ds4方式（MoEスパース活性化×mmapストリーミング）のQwen系への適用

### 1.1 ds4のレイテンシ技術（実装読み取り — [README](https://github.com/antirez/ds4)／[Issue #437](https://github.com/antirez/ds4/issues/437)／[実測レポート](https://pub.towardsai.net/i-tested-antirezs-ds4-on-18-tasks-his-one-file-c-engine-runs-a-284b-model-on-a-macbook-and-4474a6903c71)）

| ds4の技術 | 内容 | 私たちへの適用 |
|---|---|---|
| **MoEスパース活性化** | 284B中トークン毎に約1/10のみ活性。26.7 t/s生成・58.5 t/s prefill（M3 Max 128GB） | **Qwen3-30B-A3B**（30.5B総/3.3B活性）＝QwenファミリーのMoEでそのまま適用可 |
| **SSDストリーミング×先読み** | 素のストリーミングは**1トークン10〜20秒で実用不能**（1GB/sディスク）。**レイヤー順処理を利用し次レイヤーのエキスパートを先読み（ダブルバッファ）**してディスク遅延を隠蔽 | llama.cppはmmap＋OSページキャッシュで自動。**WindowsのOS先読えは弱い**ため、初回コールドは遅くウォームで実速（下記実測） |
| **エキスパート常駐キャッシュ** | ホットエキスパートをRAMに保持。「SSD→フル常駐へ8秒」 | OSページキャッシュが同等機能（llama.cpp mmap既定） |
| **ルーテッド専門家のみ粗量子化** | ルート専門家はQ2/Q4でも品質耐性大 | UD-Q3_K_XL（12.9GB）→ 15.4GB機でほぼキャッシュ収容 |
| **圧縮KV＋SSD KVスナップショット／prefixpreload** | 会話prefixの再prefill回避 | llama-serverのスロットprefixキャッシュで既に実装済み（-96%実測） |
| MTP投機的デコーディング | オプトイン | Qwen3-30Bは非対応MTP。gpt-ossのEAGLE3相当は無いが不要な速度が出ている（下記） |
| prefillチャンク分割 | 2048トークン区間 | `-ub 512`で実装済み |

### 1.2 実測（本マシン: Ryzen 7 5700U / RAM 15.4GB / NVMe / llama.cpp b10936）

**原理実証（gpt-oss-20b MoE, 11.28GB, `--no-repack`でmmapストリーミング）**:

| 指標 | 20B MoE（活性3.6B） | 4B dense（現行） |
|---|---|---|
| 生成 tg | **10.4〜10.5 t/s** | 10.1 t/s |
| 初回（コールド） | tg 7.8 t/s（SSDストリーミングしつつ） | — |
| 品質 | 20B級 | 4B級 |

→ **トークン速度を一切落とさずモデルを5倍に巨大化できることを実証**（ds4と同じ原理）。CPU_REPACK（RAM内重みコピー）はmmapストリーミングと排他のため`--no-repack`必須。

**Qwen3-30B-A3B UD-Q3_K_XL（12.88GB）実測（2026-09-13、c2048/ub256/--no-repack）**:

| 指標 | **Qwen3-30B-A3B MoE（活性3.3B）** | 現行 Qwen3-4B dense |
|---|---|---|
| **生成 tg** | **14.1 t/s** | 10.1 t/s |
| pp（プロンプト処理） | 13.2 t/s（コールド） | 46.4 t/s |
| **ウォームE2E**（短文質問） | **約1.4秒** | 約10秒 |
| 正答 | 「1,500円」「3日」とも正答 | 同 |
| 品質クラス | **30B級** | 4B級 |
| ファイル | 12.88GB（UD-Q3_K_XL） | 2.32GB |

→ **ds4の本質をQwen系で実証**: MoEのスパース活性化（1トークンあたり3.3Bのみ）により、**4B denseより生成が40%高速で、品質は7.6倍の30B級**。プロンプトが短いRAG用途ではpp低下も実用範囲。

**注意**: 12.9GBファイル×15.4GB RAMでは余裕が薄い。16GB実機でembed+rank常駐と同居させるにはQ2_K_XL（11.0GB）の検討も。

## 2. 課題の本質対応（精度・堅牢性）

| # | 課題 | 本質対応 | 検証方法 |
|---|---|---|---|
| A1 | ガード誤拒否（1/19） | 固定閾値を**多シグナル判定**へ置換: リランクtop1スコア＋ハイブリッドcos＋キーワード被覆率の3信号を組み合わせ（単一閾値は分布の裾に弱い）。閾値はgolden QA 100問で再較正 | 拡充golden QA（100問）の誤拒否0件＋ナレッジ外50問の検出率100% |
| A2 | golden QA が10問と少ない | **100問へ拡充**（既存知識から自動生成＋手動レビュー）。CIで自動採点する土台に | 全構成（1.7B/4B/MoE）で共通使用 |
| A3 | PDF簡易抽出の限界 | **PdfPig導入**（フェーズ2予定を前倒し）。CIDフォント・日本語PDF対応 | 実業務PDFサンプル10件の取り込み率 |
| A4 | Web検索のレート制限 | **複数エンジンfallback**（DDG→Bingスクレイプ→Brave API無料枠）＋上位1件のページ本文取得（5秒タイムアウト、SSRFガード適用） | 連続20問で全成功率≥90% |
| A5 | キャッシュが文脈を無視 | キャッシュキーに「直前の質問のハッシュ」を含める（文脈違いの同一質問は別エントリ） | follow-up質問でキャッシュが誤ヒットしないこと |
| A6 | 8GB実機未検証 | クイック階級（1.7B）を8GB実機（またはRAM制限VM）でE2E検証 | 25問soakで平均≤8秒 |

## 4. 実行順序

1. **本日**: MoEスパイク（gpt-oss-20bベンチ＋golden QA簡易10問）→ 採否判断
2. **+2〜3日**: A1多シグナルガード＋A2 golden QA 100問拡充＋B1リランク省略（セットで検証）
3. **+1週間**: MoE quality tier 実装（モデルマネージャのカタログ追加＋`--spec-draft-model`対応）／A3 PdfPig／A4 Web複数エンジン
4. **+2週間**: A5キャッシュキー／A6 8GB実機／B2 Vulkan再検証
5. **継続**: WPFシェル・サービス化・インストーラ（フェーズ3、Store申請要件どおり）
