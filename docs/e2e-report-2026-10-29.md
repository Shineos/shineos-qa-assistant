### 0.5 8GB実機E2Eの代替検証（実機なしで実施可能な範囲）

8GB実機が手元にないため、**リサイクル閾値を設定で強制下げる**方式で8GB機のポリシー経路をこの機体で実証した:

- 新設の設定キー `recycle_threshold_mb` で閾値（MB）を上書きできる（未設定=RAM自動: 8GB機2,200MB / 16GB機4,500MB）。16GB機で8GB機のポリシーを再現する検証・搭載RAMと実態が乖離する環境の調整に使える
- 1,700MBに強制してQA 23チャンク＋7問×2巡（14問）を投入: **リサイクル5回発火**（1,848〜1,906MBで検知）、毎回「recycled and prewarmed」が**約1〜2秒で**完了し、リサイクル直後の質問の応答速度は暖機ベースラインと同等（体感遅延なし）。WSは1,658MBで頭打ち、**14問すべて合格・品質劣化なし**
- 本検証で担保されるのはリサイクル経路の挙動（閾値検知・停止→再起動・先行暖機・回答品質）。実8GB RAMでのOSレベルの圧迫（他アプリ併走）は実機での確認が必要

**→ 10-30追加: RAM圧迫下での118問フルE2E（8GB実機に最も近い検証）**。15.35GB機に約2.4GBのメモリホグを投入して空き物理メモリを8GB機ピーク相当（1.7〜2.3GB）に下げ、**8GB実閾値2,200MB**（`recycle_threshold_mb: 2200`）でGolden QA 118問を連続実行した:

| 項目 | 結果 |
|---|---|
| スコア | **116/118** — 無圧迫ラン（116/118）と同一スコア・同一不合格（t25/t49 = 既知のリランカー揺らぎ）。**RAM圧迫による劣化ゼロ** |
| リサイクル | **7回発火**（2,311〜2,313MBで検知 → 毎回約2秒で「recycled and prewarmed」・prewarm失敗0件） |
| LLMワーキングセット | 1,746〜1,984MBに抑制（閾値2,200MB以下を維持） |
| エンジン生存性 | 全プロセス生存。ページングはホグの冷えたページが退避し、アクティブなエンジンは保護される（実8GB機と同じOS動作） |
| 完走後 | ホグ撤去・自由メモリ7.45GBに復帰。応答も正常 |

この検証で担保される範囲: 大きなコミットメモリ負荷の下でのリサイクル無限ループなし・エンジンOOMなし・回答品質不変・先行暖機の実効性。実8GB機との残差はCPU性能・ディスクキャッシュの冷え方・他アプリ構成であり、これらは実機での確認事項として残る。

## 6. 2026-10-30 後半 — 残りギャップの対応（実績列の訂正・FAQ候補・多言語検証）

### 6.1 実績表の列マッピング手動訂正（スキーマv5）

自動検出はヘッダラベル（見積額/原価/納期等）頼みのため、列名が違う実績表で見積・原価が集計されない問題への対応。

- ナレッジの実績集計に列の役割（図番/見積/原価/納期）の**ドロップダウン編集**を追加。「この列設定で実績辞書を作り直す」で元ファイル（data/files配下に常時保存）を再パースし、jisseki_metaを作り直す（PUT /api/jisseki/{id}/columns）。集計API・図面QAへの実績注入はjisseki_metaを読むため自動反映
- 設定は jisseki_colmap テーブルに保存（次回起動後も有効・GETはmanual=trueで返す）。誤設定は保存時ブロック（図番未指定・同一列への複数役割・抽出0件）
- 実測（金額A/金額B/日付という自動検出不能なCSV）: 自動検出で見積0件 → PUT上書き → **4件再抽出・見積合計460,000円/原価平均70,000円** を確認。エラー系3ケース（図番未指定/重複/役割解除）も確認

### 6.2 FAQ候補の自動生成（👎フィードバック → 編集採用）

- 👎評価（message_id指定）で、その質問×回答（＋コメント・修正案）を faq_candidates テーブルへ自動保存。拒否回答（該当なし）は対象外、同一質問のpending重複もスキップ
- FAQ管理UIに「👎フィードバックからの候補」を追加: 質問/回答を編集して**FAQとして採用**（即答として登録・次回からLLM不使用）または削除
- 実測: 質問→👎→候補生成→編集採用→**同一質問が4msの即答に切り替わる**ことを確認（採用後のFAQはpublished）

### 6.3 多言語（vi/zh/id/tl）品質検証 — 5/32 → **31/32**

4言語×8問=32問の検証セットを新設（`scenarios-multilingual.json`、期待値は数字中心で言語非依存）。scenario-test.ps1に `lang` フィールド（answer_lang送信）を追加。

| 言語 | 初回 | 最終 |
|---|---|---|
| vi（ベトナム語） | 0/8 | **8/8** |
| zh（中国語簡体） | 2/8 | **8/8** |
| id（インドネシア語） | 2/8 | **8/8** |
| tl（タガログ語） | 1/8 | 7/8 |
| 合計 | 5/32 | **31/32** |

失敗の根本原因と対策:

1. **語彙一致ゼロ**: 外国語クエリと日本語KBでkw=0.00となりlow-confガードが全拒否 → 対応言語の基本語彙（密码/mật khẩu/kata sandi、酒店/khách sạn/penginapan、会议室/phòng họp/ruang rapat等）を正規トークン辞書（MfgTerms）へ追加し、canonicalEvidenceで拒否を免除
2. **大文字不一致**: 「Mật khẩu」（文頭大文字）が別名「mật khẩu」にOrdinal一致しない → 非ASCII別名を大文字小文字非依存に修正
3. **リランカーの外国語不信**: bge-rerankerはvi/id/tl×日本語ペアを正しく評価できず（top1 -6.7等）、ガード拒否になる → **クロスリンガル救済**を追加: 外国語クエリ（かなを含まない・IsForeignQuery）に限り、正規トークンで辞書を直接引き（SearchCanonical）、プール外の正解チャンクでも回答する
4. 救済の発火条件を外国語に限定した理由: 日本語の拒否質問（KBに無い話題: パスワード管理ツールのおすすめ等）でも救済が発火し、拒否ではなく無関係回答を生成する退行が発生したため（t77〜t80実測 → IsForeignQueryゲート追加で復旧を確認）

残存: tl 1問（会議室定員。タガログ語出力時の数値抽出が小型モデルの限界）。多言語ユーザーへの実用上の提案: 重要な横断質問はstandard階級（§0.4の実測で承認者系の揺らぎが消える）。
