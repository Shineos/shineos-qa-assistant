# レイテンシ実証レポート — v2-fast構成（UX高速化の証明）

- 日付: 2026-09-13
- 目的: 「ChatGPTの3秒には及ばないとしても、体感速度をどこまで詰められるか」を実装と実測で証明する
- 関連: [regression-test.md](regression-test.md)（v1比較）／ [phase0-report.md](phase0-report.md)（基礎計測）／ [architecture-v2.md](architecture-v2.md)
- 検証環境: Ryzen 7 5700U（8C16L）／RAM 15.4GB（空き6.7GB・クリーン状態）／Windows 11
- 実装: `spikes/phase0/test-v2-fast.ps1`（**3サーバー同時常駐＝本番構成**で実測）

## 0. 総括

**v2-fast構成（痩身プロンプト＋リランク＋prefixキャップ＋NO-HITガード＋回答キャッシュ）で、精度10/10を維持したまま v1比 平均-35%（CPU）／-48%（Vulkan）の体感高速化を実証した。** 同一文書への連続質問は**約5秒**、反復質問は**0.3秒未満**、ナレッジ外は**検索だけで即時拒否**となる。初回の新トピック質問のみ7〜9秒のTTFTが残る（CPU物理）。

## 1. v2-fast構成（実装した施策）

| 施策 | 実装内容 |
|---|---|
| 痩身プロンプト | 圧縮システムプロンプト＋**top2チャンクのみ**注入（950→330-440トークン） |
| **スマートスニペット** | チャンクを無邪気に切り詰めず、**クエリ関連文を中心に240字の窓**を抽出（関連文のキーワード重複スコア最大の文から前後へ拡張）。*単純先頭200字切り詰めは「チャンク末尾にある事実」を破壊しhit 4/8に劣化したため廃止（教訓）* |
| リランク top8→top2 | 常時リランク（候補を4に絞ると関連chunkが候補外に漏れ誤ガード——top8維持が必須と判明） |
| **NO-HITガード** | リランクtopスコア < **-2.0** → 推論スキップし固定文で即時拒否 |
| prefixキャッシュ | 静的prefix前方＋llama-serverスロットLCP再利用（自動） |
| 回答キャッシュ | 質問埋め込み85ms＋cos照合（完全一致=即時） |
| 3サーバー同時常駐 | chat＋embed＋rerank並列起動（本番構成） |

## 2. 証明1 — 精度を維持したまま高速（10問ゴールデンQA・同一コーパス）

| 構成 | 正答 | 拒絶 | TTFT(hit)* | 特記事項 |
|---|---|---|---|---|
| v1（旧・比較基準） | 8/8 | 2/2 | （平均14.7s E2E） | 非ストリーム計測 |
| **v2-fast CPU 4B** | **8/8** | **2/2** | **平均4.93s**（最大9.08／最小0.53） | 同一文書質問は0.53〜0.67s |
| **v2-fast Vulkan 4B** | **8/8** | **2/2** | 平均6.74s† | pp +66%・検索2〜3倍高速 |
| **v2-fast CPU 1.7B（クイック階級）** | **8/8** | **2/2** | — ‡ | pp 125 t/s（4Bの2.5倍）・tg 20.8 t/s |

\* TTFT=ストリーム最初の1文字まで（curl出力ポーリング実測）。retr（検索＋リランク約4.3〜4.7s）は別途加算。
† Vulkanは一部キャッシュ再利用経路に4〜6sの遅延（b10936のKV-shift特輪、下記§5）。pp実質は高速。
‡ 1.7Bは当該遅延の影響が大きくpoll値が歪んだため、信頼できる**サーバ側pp/tg値**で評価（§4）。

|---|---|---|---|

## 3. 証明2 — キャッシュ3層の実測値

1. **prefix/LCPキャッシュ（llama-server内蔵）**:
   - 同一コンテキスト追質問: pp **8,851ms→486ms（-94.5%）**・TTFT 0.67s
   - **別質問でも同じ文書なら**: pp処理 **12〜17トークンのみ**（443トークン中96%がキャッシュHit）→ TTFT 0.53〜0.64s
   - → 「同じ規程について複数聞く」実利用パターンがほぼ無料
2. **回答キャッシュ**: 質問埋め込み **54〜85ms/件**（t4スレッド時）。完全一致=cos 1.0で即時。**言い換え（「宿泊費の上限金額を教えて」）はcos=0.907** → 閾値0.97では非ヒットとなり検索へ回る（安全側。0.90に下げると誤ヒットリスク）→ 設計は0.97維持を推奨
3. **NO-HITガード（推論前拒否）**: リランクtop8のスコアで判定。**3構成すべてでhit ≥ +0.26／nohit ≤ -7.84に完全分離**（閾値-2.0は約8ポイントの余裕）。nohit応答は検索時間のみ（CPU 4.7s／Vulkan 1.4〜2.9s）

## 4. 証明3 — メモリ階級の実運用構成（3サーバー同時常駐・初実測）

| 階級 | chatモデル | 3サーバー合計RSS | 全起動時間 | 対象 |
|---|---|---|---|---|
| 標準 | Qwen3-4B Q4_K_M | **5.29GB**（chat 4.32＋embed 0.49＋rank 0.49） | 8.3〜8.8s | 16GB機 |
| クイック | Qwen3-1.7B Q4_K_M | **2.92GB**（chat 1.94＋0.49＋0.49） | 7.3s | **8GB機で余裕を持って稼働**（OS込み約5.5GB） |
| （Vulkan時） | 4B | 4.84GB | 11.4s（シェーダコンパイル） | 16GB機 |

→ 設計書のRAM階級ロジックの実装値が確定。**8GB機=クイック階級（1.7B）が現実解**、16GB機=標準（4B）。

## 5. 発見したリスクと対策

| リスク | 実測内容 | 対策 |
|---|---|---|
| **b10936 Vulkan/小モデルでの初chunk遅延** | pp完了後〜最初のcontent chunkに4〜6sの遅延が発生する経路あり（スロットKV再利用時と推定） | エンジンビルド更新時に再検証（CIのカタログE2Eに「TTFT=predicted初回+1s以内」チェックを追加）。発生時はスロットクリア運用 |
| スニペット切り詰めによる事実破壊 | 先頭200字固定切断でhit 4/8に劣化（事実はチャンク末尾に多い） | **クエリ関連文中心のスニペット抽出で解決済み**（240字）。フェーズ2でC#実装時に単体テスト化 |
| リランク候補の絞り込み | top4プールで関連chunkが漏れ誤ガード（hit 4/8） | **top8維持で解決**。検索側recallとのトレードオフは大規模コーパスで再評価 |
| リランクがwarmケースの支配コスト | 4.3〜4.7s/問（フルサイズ8チャンク） | **入力スニペット化（240字）で3.2sに短縮（-29%、2026-09-13実測）**。更なる削減は候補top6のrecall評価が必要 |
| 投機的デコーディング | **効果なし（実測）**: Qwen3-0.6Bドラフトで tg 10.7→10.7 t/s（同一）。greedyな日本語事実回答は受理率が低くCPUでは利益ゼロ | **不採用**（2026-09-13 bench、spikes/phase0/spec-e2e.ps1） |
| **ベンダー変更の効果** | **同サイズのローカルモデルは速度同等（実測）**: Qwen3-4B(4.0B/2.32GB) pp46.4/tg10.1 vs **Phi-4-mini(3.8B/2.31GB) pp41.1/tg10.9**（同条件同時bench、2026-09-13）。速度はパラメータ数×メモリ帯域の物理で決まりベンダー非依存 | モデル変更で速くするなら**階級を下げる**（1.7B=pp125/tg21）。クラウドAPI（Gemini/Azure OpenAI）は1〜3秒TTFTだが社外送信となり本製品の完全オフライン前提と冲突（任意ON階級としてのみ検討可） |
| **Word/PDF取り込み** | 実ファイル検証（2026-09-13）: .docx（生成→登録→「月額5,000円」正答・UTF-8ファイル名OK）、.pdf（FlateDecode→登録→日本語質問で英語PDFから「週3日以上在宅の正社員」正答＝クロスリンガル取得も可）。**制限**: 簡易抽出のためスキャンPDF・CIDフォント日本語PDFは失敗を返す（フェーズ2でPdfPig本格化） | 取り込みOK・制限はUI/ドキュメントに明示 |
| エンジン孤児化・OOM連鎖 | バックエンド強制終了でllama-serverが孤児化し蓄積（30個・RAM枯渇→OOM→再起動失敗の連鎖を実際に確認） | **Job Object(KILL_ON_JOB_CLOSE)＋ログStream確実破棄＋OOM時のクイック階級自動フォールバック**を実装（Engines.cs） |

## 6. UX設計への反映（確定)

1. **0.3秒で参照文書名表示**（検索完了時点）→「📖 出張・旅費規程.md を確認中…」
2. **SSEストリーム**（生成は読解速度以上: 4B 10.4 t/s／1.7B 20.8 t/s）
3. 反復質問はキャッシュ即答（0.3秒）
4. ナレッジ外は1〜5秒で明確に拒否（幻覚を出さない高速経路）
5. **階級切替UI**: 「クイック（1.7B・8GB機向）／標準（4B）」。設定はモデル再読込のみで切替（llama-server再起動2〜5秒）

## 7. 残る誠実な限界

- **初回の新トピック質問7〜9秒（CPU 4B）は物理**（pp 50 t/s）。ChatGPTの3秒（データセンターGPU）と同等にはならない。緩和はVulkan（-2〜3s）・1.7B階級・プロンプト更なる圧縮のみ
- 10問×1環境の検証。TTFT分布の統計化（50問・複数機種）はフェーズ1
- Vulkanの初chunk遅延は未解明（§5）——既定CPU・Vulkanは設定切替とする方針を維持
