# 機能プラン: 図面PDF検索・Q&A（製造業向け拡張）

- **ブランチ**: `feature/drawing-search`
- **作成日**: 2026-09-20
- **位置づけ**: 製造業特化（方向1）の第一具体物。社内知恵袋の既存RAGパイプラインを**拡張**するもので、プロダクトのフォーク・新アプリ化はしない
- **前提調査の結論**（2026-09-20）:
  - Microsoft Store日本市場で「図面検索」「図面管理」は**空白**（専用アプリゼロ）。CAD/ビューア層（AutoCAD・DWG FastView・RootPro CAD等）は既存ベンダーが埋めており、当機能はこれらと**競合せず補完**する
  - 製造業の接受渡し成果物はPDF図面が主体で、**CAD出力PDFはテキスト層を持つ**（OCR不要）
  - 決定事項: 「CADデータ検索（形状類似・DWG/DXFネイティブ解析）」は行わない。対象は**図面PDFの取り込み・メタデータ化・検索・Q&A**に限定する
  - 決定事項（入力経路）: 最頻出の場面は「図面を見ながら周辺知識を聞く」であり、図番の手動転記が利用の摩擦になるため、**キャプチャ・写真入力（内蔵OCR＋確認チップUI）を第2の入力経路として採用**（§3.6）。視覚モデルによる図面理解は製品の土台（CPUのみ・低スペック・ダウンロード増なし）と衝突するため対象外
  - 決定事項（アーキテクチャ）: 本機能は本体機能ではなく、**設定画面からON/OFFする「拡張パック」として提供する**（§3.0）。既定OFF・ShineosQAの基本フロー（チャット＋ナレッジ取り込み）は不変

## 1. スコープ

### やる（Phase A・本プラン）

| # | 機能 | 内容 |
|---|---|---|
| A0 | PDFテキスト抽出の本格化 | 現行の自製抽出器（CJK CIDフォント非対応）を適切なライブラリに置き換え、日本語CAD出力PDFからテキストを確実に抽出。**全PDFの品質改善でもあり、図面機能の前提** |
| A1 | 元ファイルの保持とサムネイル | 取り込み時に元PDFをローカル保存し、1ページ目のサムネイルPNGを生成。ナレッジ一覧に表示 |
| A2 | 表題欄（タイトルブロック）の構造化 | 図番・品名・材質・尺度・改訂・承認日をメタデータ化。図番の**表記ゆれ正規化**（`A-1234-B` ↔ `A1234B`）を索引・クエリ両面に適用 |
| A3 | 検索・UI強化 | 図番・品名・材質によるフィルタ/検索、種別バッジ、出典の図面表記、「元の図面を開く」ボタン |
| A4 | 掲載物への反映 | README・Store掲載文（`docs/store-submission.md` §7）へ「図面検索」を追加 |
| A5 | キャプチャ・写真で質問 | チャットに画面キャプチャ・クリップボード画像・（Stage 2で）紙図面の写真を貼って質問。OS内蔵OCRで図番等を認識し、**確認チップUI**で1タップ修正して検索（§3.6）。テキスト入力と並ぶ第2の入力経路。A0〜A3と**独立に並行着手可能** |
| A6 | 拡張パック機構 | 上記A1〜A5を**設定画面「拡張機能」のスイッチの内側**に置く機構（§3.0）。既定OFF・本体フロー不変。A0はパック対象外（常時適用の本体品質改善） |

### やらない（明確に線を引く）

- DWG/DXF/SolidWorks等ネイティブCADファイルの解析・変換
- 形状類似検索（3Dジオメトリ比較。EXALEAD OnePart等のエンタープライズ市場）
- アプリ内CADビューアの自作（「規定アプリで開く」で充足）
- スキャン図面PDF（テキスト層なし）の**取り込み側**OCR → **Phase C** で需要確認後に検討（※質問側の写真入力A5とは別。A5は検索クエリ生成が目的）
- Excel/CSV取り込み（QC工程表等）→ **別プラン**（本プランの後続候補）
- 共有フォルダの監視・自動同期 → Phase C候補（手動のフォルダ一括取り込みは既存APIで可能）
- **視覚モデル（VLM）による図面理解**（画像内の寸法・公差の読み取り、形状比較）→ CPUのみ・8GB・ダウンロード増なしという製品の土台と衝突するため対象外。将来の「高品質tier」の検討課題とするのみ

## 3. 設計

### 3.0 拡張パック機構（本プラン全体の前提アーキテクチャ）

**方針**: 「図面PDF検索・Q&A（製造業向け拡張）」は本体に直接組み込まず、**設定画面の「拡張機能」カードからON/OFFする拡張パック**として実装する。**既定はOFF**。OFFの間、本体の画面・操作・取り込みは現行と完全に同一（チャット＋ナレッジ取り込みの基本フロー不変）。

**この構造を採る理由**:
1. 本体は「社内知恵袋」として汎用のまま。製造業向けは利用者が選んで後付けする——業界特化と汎用性の両立
2. 既存ユーザーへの回帰リスクをゼロにする（新機能が本体フローを一切変更しない）
3. パック機構自体が「同一コアから業界別機能を生む」プラットフォーム戦略の足場になる。将来の建設・介護パック、Excel/CSV取り込み等も同じ機構に乗る

**実装（既存パターンの踏襲）**:

| 箇所 | 内容 |
|---|---|
| 設定保存 | SQLite `settings` テーブル（key-value）に `ext.drawing = "0"/"1"`。`web_search`・`bg_friendly` と同じ `/api/settings` の経路を使う（`Program.cs:51`。config.json＝エンジン設定には置かない） |
| 設定UI | `settings.ts` に「拡張機能」カードを追加。`setting-row`＋スイッチの**既存パターンどおり**（Web検索トグルと同形・`settings.ts:26-33` 参照）。タイトル「図面PDF検索・Q&A（製造業向け）」＋説明文＋取り込み済み図面件数＋「無効化しても取り込んだ図面データは残ります」の注記 |
| バックエンド | 拡張パック定義（Id/名称/説明/既定値）を1箇所に集約。`Ingest`の図面分岐・`/api/ocr`・サムネイル/元ファイルAPI・UI向け状態公開がすべてこの定義とフラグを参照。**フラグはリクエストごとに読む（再起動不要・即時反映）** |
| 状態公開 | `/api/settings` の応答に `extensions: { drawing: true/false }` を追加。UIはこの値でキャプチャボタン・バッジ・フィルタの描画を判定 |
| OFF時の挙動 | 図面判定・元ファイル保存・表題欄抽出を行わない。`/api/ocr` 等のパック専用エンドポイントは無効応答。`drawing_meta` 等のテーブルは `CREATE TABLE IF NOT EXISTS` で常に作成してよい（空のまま・スキーマ移行の複雑化を避ける） |
| ON→OFF | **データは削除しない**（UI上は非表示になるのみ）。ナレッジ一覧では通常文書として残る。再ONで復帰 |

**適用範囲の明確化**: A0（PdfPigによるPDF抽出器置換）は**パック対象外**。日本語PDF全般の文字化け対策という本体の品質修正のため、パックOFFでも常時適用される。

### 3.1 A0: PDFテキスト抽出の置き換え

- 候補: **PdfPig**（.NET・Apache-2.0・ToUnicode CMap対応・テキスト座標取得可）。座標情報はA2の表題欄領域判定にそのまま使うため、抽出と座標を一体で供給できるPdfPigが本命
- PDFium系（サムネイル用、A1）と役割分担: **テキスト=PdfPig、レンダリング=PDFium**（PdfPigはレンダリング非対応）
- 既存の自製抽出器はフォールバックとして残すか削除するかは実装時に決定（PdfPigで抽出ゼロのPDFを自製で救えるケースは少ないと想定し、基本は置き換え）
- 受け入れ基準: 日本語を含むCAD出力PDF・一般的な日本語PDFでテキストが正しく抽出されること（サンプルcorpusで判定）

### 3.2 A1: 元ファイル保存・サムネイル

- 保存先: `data/files/<file_id>.pdf`（`knowledge.db` と同じローカル配置。外部送信なし・プライバシー方針の変更なし）
- サムネイル: 1ページ目を幅300px程度のPNGにラスタライズ（PDFium）。`files` に `thumb BLOB` または `files` と別テーブルに保存。アンインストール時の削除確認フローは既存データと同一扱い
- サイズ上限: 既存の100MB/ファイル制限（`Program.cs:164`）を継承
- 破損・テキスト層ゼロPDFの扱い: **エラーにせず「メタデータなし図面」として登録**（テキスト抽出失敗でもサムネイルとファイル名で資産化）。ただしチャンクがゼロになるため検索対象外であることをUIに表示

### 3.3 A2: 表題欄の構造化と図番正規化

**図面の判定**: 取り込み時、PDFの特徴（テキスト量が少ない・ページ数1・図番らしいパターンの存在）で `files.kind = 'drawing'` を付与。誤検出はUIで手動変更可能にする。

**表題欄抽出（2段構え）**:
1. **ルールベース（第一段）**: PdfPigの座標でページ右下領域（JIS慣行のタイトルブロック）のテキストを集約し、正規表現で図番（英数字+記号の複合パターン）・改訂記号（A/B/C…、数字）・日付を抽出。品名・材質は隣接テキストから
2. **LLM構造化（第二段・設定ON時）**: 抽出テキストをクイック1.7Bに渡しJSON（`{zuban, hinmei, zairyo, kotei, kaisetsu}`）で構造化。ローカル完結・コストゼロ。精度はルールベースのフォールバックとして位置づける

**図番正規化（成否の鍵）**:
- 正規形キー: NFKC正規化 → 英数以外の記号・空白を除去 → 小文字化（例: `A - 1234－B` → `a1234b`）
- 適用箇所: (a) 索引側（図面チャンクのトークンに正規形を追加）と (b) クエリ側（質問文中の図番らしきトークンを正規形に変換）の両面。片側だけでは不一致が残る
- 実装方針: `Rag.Tokenize` に「記号を含む英数字連結」トークン（例: `[A-Za-z0-9][A-Za-z0-9\-_／/]*` 相当）を追加し、索引トークンとして正規形を併せて持たせる。**全ドキュメントのトークンが変わるため、取り込み済みデータの再索引と `PromptVersion` 更新（回答キャッシュ無効化）が必要**

**メタデータ保存**:

```sql
CREATE TABLE IF NOT EXISTS drawing_meta(
  file_id INTEGER PRIMARY KEY REFERENCES files(file_id) ON DELETE CASCADE,
  zuban_raw TEXT, zuban_norm TEXT, hinmei TEXT, zairyo TEXT,
  scale TEXT, revision TEXT, approved_at TEXT);
```

**チャンク構成**: 図面は1枚1チャンク。チャンクテキストは `【図面】図番: A-1234 / 品名: ○○ブラケット / 材質: SS400 / 改訂: B` + 注記テキスト、の前置き構成にする。これにより**出典表示とRAGコンテキストが自然に図面情報を含む**（出典の列挙はバックエンドが正規化して保証する既存設計を踏襲）

### 3.4 A3: UI

- ナレッジ一覧: 種別バッジ（文書/図面）、サムネイル、図番・品名列。検索ボックス（図番正規形で部分一致・品名フルテキスト）と材質フィルタ
- チャット出典: 図面チャンクのとき `A-1234（○○ブラケット・改訂B）` の表示 + 「開く」ボタン（`data/files/<id>.pdf` を規定アプリで開く）
- 新規API: `GET /api/knowledge/{id}/thumb`、`GET /api/knowledge/{id}/file`（開く用）程度。一覧APIは `kind`・`drawing_meta` 結合に拡張

### 3.5 A4: 掲載物

- `docs/store-submission.md` §7 掲載文・§7.3 キーワード（「図面検索」「図面」を追加。7個/21単語の制約内で再編成）、スクリーンショット1枚を図面検索画面に差し替え
- README「できること」に図面検索行を追加
- 掲載文には**本体は汎用のまま「製造業向け拡張は設定から有効化」と明記**する（実態と一致させ、汎用ツールとしてのポジションを維持する）

### 3.6 A5: キャプチャ・写真で質問（OCR入力補助）

**必要と判断した理由**（2026-09-20 方向性検討の場面分析）:
- 製造業での最頻出の質問形態は、**図面を見ながら、図面に書いていない周辺知識（検査基準・作業標準・過去の不具合対策・代替材）を聞く**場面。図面自体に書いてあることは自分で読めば済む
- その入口で、図番の手動転記（表題欄の探索・英数記号混じりの長い図番の打ち間違い・現場での入力）が「利用される」を妨げる摩擦になる。非エンジニア向けを掲げる製品で入力だけが手入力のまま残るのは核心シーンの入口が詰まっている状態
- よって本機能は便利機能ではなく、**核心シーンの第2の入力経路**として位置づける

**設計（Stage構成）**:

| Stage | 対象 | 内容 | 判断 |
|---|---|---|---|
| 1 | 画面キャプチャ・クリップボード画像 | `Windows.Media.Ocr`（OS内蔵・**完全オフライン・日本語・モデル追加なし**。PowerToys Text Extractorと同じ経路）でOCR → 図番らしき語を抽出 → 確認チップUI → 既存検索 | 本プランに含める |
| 2 | 紙図面の写真 | Stage 1に前処理（二値化・傾き補正）を追加。汚れ・折り目で精度は落ちるが確認チップが吸収 | Pilotで紙図面比率が高ければ前倒し |
| — | 図面理解（画像内の寸法・公差読み取り） | VLM必要 | 対象外（§1 やらない） |

**成否を握る設計は精度ではなくUI**: OCR結果をそのまま検索に投げず、チャット入力欄上に「`A-1234B` で検索［修正］」のような**確認チップ**を表示し、1タップで修正できるようにする。OCRの読み間違いを致命傷にしない構造で、精度の完璧を求めない。

**実装メモ**:
- UI: 入力欄の📎横に「画面を切り取って質問」ボタン、または `Win+Shift+S` → 貼り付け。画像はチャット履歴に表示
- 図番抽出の正規表現・正規化はA2と**同じものを共用**（索引側とクエリ側で一致させることが図番検索成立の条件のため）
- API（仮）: 画像を受け取りOCRテキスト＋図番候補リストを返す `POST /api/ocr`。検索・回答は既存 `/api/chat` の経路のまま
- **最初にスパイク検証**: .NETバックエンド（自己完結publish構成）からWinRT `Windows.Media.Ocr` を呼べるか（CsWinRT経由）、ja-JP言語パックが無い環境での挙動（無効時は設定ガイド表示）

## 5. リスクと緩和

| リスク | 影響 | 緩和 |
|---|---|---|
| 表題欄レイアウトは会社ごとに異なる | 抽出精度 | ルール＋LLMの2段構え。Pilot先1社の様式に合わせて調整し、汎用性はテストcorpusで段階的に広げる |
| スキャン図面はテキスト層がない | 対象外と明言しないと期待とのギャップ | 掲載文・UIに「CAD出力PDFが対象」を明記。テキスト層なしは「メタデータなし図面」として登録し資産化 |
| トークナイザ変更は全データの再索引とキャッシュ無効化を要求 | 既存ユーザーへの影響 | 取り込み済みファイルの自動再索引処理（embedやり直し）をアップデート初回起動時に実行。`PromptVersion` 更新手順は既存規約どおり |
| ライセンス | 同梱要件 | PdfPig (Apache-2.0)・PDFium (BSD-3) を `vendor/THIRD-PARTY-NOTICES.txt` に追記 |
| 元ファイル保存でディスク使用が増える | 低スペック端末 | 図面は1ファイル数MB程度。保存ON/OFF設定と合計使用量の表示で対応可 |
| OCR精度（回転した寸法文字・細かい注記・紙写真の汚れ・折り目） | 図番認識の失敗 → 検索空振り | **確認チップUIで1タップ修正**を可能にし、精度をUIで吸収する設計。初期の照準は表題欄など水平文字ブロックに限定。紙写真はStage 2で前処理を追加 |
| WinRT OCRの利用可否・ja-JP言語パック依存 | Stage 1全体が動かない | タスク8のスパイクを最初に検証。言語パック未導入環境では機能を無効化し設定ガイドを表示（クラッシュしない） |
| 拡張のON/OFFゲート漏れ（OFFなのに図面UIが出る・元ファイルが保存される） | 「本体フロー不変」の前提が破れ、既存ユーザーに回帰リスク | ゲートは取り込み分岐とエンドポイントの**両方**に置く。**パックOFF状態でのE2Eテスト**（キャプチャボタン非表示・設定カード以外にUI変化なし・元ファイル未保存）をリリース条件に含める |

## 6. Phase B / C（本プラン外・後続）

- **Phase B**: 図面↔検査基準書↔作業標準の横断Q&A精度検証（「この型番の検査項目は？」等のevalシナリオを追加し、既存RAGのまま十分かを計測してから追加実装を判断）
- **Phase C**: スキャン図面OCR、共有フォルダ監視取り込み、Excel/CSV取り込み（別プラン）
- 将来の業界パック（建設・介護等）やExcel/CSV取り込みも**§3.0の拡張パック機構に乗せる**。本プランはその機構の最初の適用例であり、パック定義の集約・設定UI・状態公開をここで確立する

## 7. 着手前の確認事項（Pilot条件）

1. Pilot先製造業1社の図面実態: PDF化率・テキスト層の有無（CAD出力かスキャンか）・図番付番規則の統一度・表題欄様式・**紙図面の残存比率**（A5 Stage 2の前倒し判断）
2. 図番の実例サンプル（正規化テストの駆動データにする）
3. 1図面あたりの平均ページ数・サイズ（1枚1チャンク方針の検証）
4. **Pilot導入後2週間の測定設計**: SQLiteの検索クエリ履歴から「利用者が図番を手入力できているか／空振りしていないか」を確認する。打てていなければキャプチャ入力の価値が実証され、紙比率が高ければStage 2を前倒しする。**「利用された」の証拠はDL数ではなくこの利用頻度で測る**
